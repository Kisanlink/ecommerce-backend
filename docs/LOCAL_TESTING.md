# Local testing environment

How to run and test the whole backend on your machine **without touching any provider
dashboard** — no switching Razorpay to Test mode, no switching the WhatsApp number, no real
money, no real OTP messages — and with a local Firebase Auth emulator for auth.

> **The core idea:** nothing here flips a provider "mode". Razorpay **test keys and live keys
> are both always active on the same account** — the dashboard Test/Live toggle only changes
> what you *see* in the dashboard, not which keys work. So locally you just use the **test
> keys** in your local env and leave live mode off. WhatsApp OTP is generated by *our own
> backend* (not Firebase phone auth); the only part that needs the real WhatsApp provider is
> delivery, which we sidestep by injecting a Firebase-emulator token instead of running the
> OTP login. Firebase token verification is pointed at a local emulator.

---

## 0. Prod-safety rules (read once)

- **Never run the local server against the production database.** The app's real connection
  comes from `DB_POSTGRES_*` (see `cmd/server/main.go` → `GetPostgresEnvConfig`). The run
  scripts below set these to the local Docker Postgres and, because `godotenv.Load()` does
  **not** overwrite variables already in the shell, your exported local values win over
  anything in `.env`. Always launch via the script so prod `.env` values can't leak in.
- **Never set `RAZORPAY_LIVE=true` locally.** Leave it unset/empty → `GetRazorpayConfig()`
  stays in test mode.
- `sim-razorpay-webhook.mjs` and `mint-emulator-token.mjs` are **test tools** — only ever
  point them at `localhost`.
- The live `.env` (with real secrets) stays gitignored and untouched. This doc adds a
  **separate** local env you keep out of git.

## 1. Prerequisites

| Tool | Why | Check |
|------|-----|-------|
| Docker + Docker Compose | Postgres / Redis / DynamoDB | `docker --version` |
| Go (per `go.mod`) | run the backend | `go version` |
| Node 18+ | the two helper scripts (`fetch`, `crypto` built in) | `node --version` |
| Firebase CLI | the Auth emulator | `firebase --version` (`npm i -g firebase-tools`) |
| A Razorpay **test** key pair | test payments | from Razorpay dashboard → Settings → API Keys → **Test Mode** keys (`rzp_test_…`). Reading the test keys does **not** change your account's mode. |

Optional: a Delhivery **staging** token (see §6 — `/payments/create-order` checks
serviceability and fails closed, so it needs a working Delhivery call).

## 2. Start local infrastructure

```bash
cd ecommerce-backend
docker-compose up -d        # postgres :5555, redis :6379, dynamodb :8000
docker-compose ps           # all healthy
```

The compose Postgres is `DemoDB` / `postgres` / `12345678` on host port **5555**.

---

## 3. Start the Firebase Auth emulator

`firebase.json` in the repo root already configures the Auth emulator on `127.0.0.1:9099`
(UI on `:4000`). Start it with **the same project id your backend verifies against** — the
emulator's issued tokens carry that project id as `aud`/`iss`, and the backend's Admin SDK
only accepts tokens whose `aud` equals its configured `FIREBASE_PROJECT_ID`:

```bash
firebase emulators:start --only auth --project "$FIREBASE_PROJECT_ID"
```

Use your real project id (the one in your Firebase credentials) for `FIREBASE_PROJECT_ID`
everywhere in this doc, so the emulator, the backend, and the minted tokens all agree.

> You keep your **real** Firebase credentials in the local env only so `InitFirebase()` can
> construct the Admin SDK. With `FIREBASE_AUTH_EMULATOR_HOST` set, the SDK talks to the
> emulator and **never contacts Google** for token verification or user lookups — the real
> key is not used to sign or verify anything.

## 4. Run the backend against local infra

Create `.env.local` in `ecommerce-backend/` (keep it out of git) and a launch script. The
launch script exports the values so they override `.env`.

### `.env.local` (template — fill in the bracketed values)

```dotenv
# --- Local Postgres (Docker) : overrides any prod DB in .env ---
DB_POSTGRES_HOST=localhost
DB_POSTGRES_PORT=5555
DB_POSTGRES_USER=postgres
DB_POSTGRES_PASSWORD=12345678
DB_POSTGRES_DBNAME=DemoDB
DB_POSTGRES_SSLMODE=disable

# --- Local Redis (Docker) ---
REDIS_HOST=localhost
REDIS_PORT=6379
REDIS_PASSWORD=

# --- Razorpay TEST keys (both test+live keys are always active; no dashboard change) ---
RAZORPAY_KEY_ID=rzp_test_xxxxxxxxxxxxx
RAZORPAY_KEY_SECRET=[your test key secret]
RAZORPAY_LIVE=
# Any local string — the webhook simulator signs with the same value:
RAZORPAY_WEBHOOK_SECRET=local_webhook_secret
# Leave the 1CC secret UNSET so Magic Checkout callback signature stays dormant locally:
# RAZORPAY_MAGIC_CHECKOUT_SECRET=

# --- Firebase: real creds so the Admin SDK constructs; emulator host routes it local ---
FIREBASE_PROJECT_ID=[your firebase project id]
FIREBASE_SERVICE_ACCOUNT_PATH=firebase_service_account.json
FIREBASE_AUTH_EMULATOR_HOST=localhost:9099

# --- WhatsApp: leave unset so WhatsAppService.IsEnabled() == false (no real messages) ---

# --- Delhivery: staging so /payments/create-order serviceability passes (see §6) ---
DELHIVERY_PRODUCTION=
DELHIVERY_BASE_URL=[delhivery staging base url, if you use one]
# DELHIVERY_API_TOKEN / related vars as your config expects

PORT=8080
GIN_MODE=debug
```

### Launch (PowerShell — Windows) — `scripts/local/run-local.ps1`

```powershell
# Load .env.local into THIS shell, then run. Shell vars beat .env (godotenv won't overwrite).
Get-Content .env.local | Where-Object { $_ -match '^\s*[^#].*=' } | ForEach-Object {
  $kv = $_ -split '=', 2
  [Environment]::SetEnvironmentVariable($kv[0].Trim(), $kv[1].Trim(), 'Process')
}
Write-Host "DB -> $($env:DB_POSTGRES_HOST):$($env:DB_POSTGRES_PORT)/$($env:DB_POSTGRES_DBNAME)  (must be localhost:5555)"
go run ./cmd/server/main.go
```

### Launch (bash)

```bash
set -a; . ./.env.local; set +a
echo "DB -> $DB_POSTGRES_HOST:$DB_POSTGRES_PORT/$DB_POSTGRES_DBNAME  (must be localhost:5555)"
go run ./cmd/server/main.go
```

Confirm on boot: the log line `NeonDB Configuration` must show **host=localhost,
port=5555** (and `is_neondb=false`). If it shows a `neon.tech` host, stop — your prod DB
leaked in; fix the env export. The models (including the new `payment_cart_snapshots` table)
auto-migrate on start. Health check: `curl http://localhost:8080/health`.

## 5. Get an auth token (no WhatsApp, no Google)

Instead of running the WhatsApp-OTP login (which would need the real WhatsApp provider and a
Google custom-token exchange), mint a token straight from the emulator and let the backend
auto-provision the local user:

```bash
FIREBASE_PROJECT_ID=[your project id] \
  node scripts/local/mint-emulator-token.mjs tester@local.test Test123!
```

It prints a `UID` and an `ID TOKEN`. Export the token for the calls below:

```bash
TOKEN=<paste the ID TOKEN>
```

The **first** authenticated payment call auto-creates the matching local user for that UID
(`mapFirebaseUIDToInternalUserID` → Admin SDK `GetUser` against the emulator →
`CreateGoogleUser`). No manual SQL needed.

> Need a specific pre-existing user instead? Point its row at the emulator UID:
> `UPDATE users SET firebase_uid = '<UID>' WHERE id = '<USERxxxx>';` (column `firebase_uid`).

## 6. End-to-end: a normal test payment

1. **Add a shipping address** and **add cart items** using `TOKEN` against the authenticated
   APIs (`POST /api/v1/cart/items`, and your addresses endpoint). Note the address id.
2. **Create the Razorpay order (writes the snapshot):**

   ```bash
   curl -s http://localhost:8080/api/v1/payments/create-order \
     -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
     -d '{"first_name":"Test","last_name":"User","mobile":"9999999999","shipping_address_id":"<ADDR_ID>"}'
   ```

   Returns a Razorpay `order_id` (`order_…`) and the test `key_id`.

   > `create-order` calls Delhivery **serviceability and fails closed** (#23): if Delhivery
   > errors or the pincode isn't serviceable you get `503`/`400` and no order. Use a
   > serviceable pincode and working Delhivery **staging** creds (`DELHIVERY_BASE_URL` /
   > token) in `.env.local`. This is also why the address must be real (valid 6-digit
   > pincode, real city/state — placeholders are rejected before payment).

3. **Pay with a Razorpay test instrument.** Open the hosted checkout
   (`/api/v1/payments/checkout?order_id=<order_id>`) or your frontend pointed at this backend,
   and pay with a Razorpay **test** card/UPI (e.g. card `4111 1111 1111 1111`, any future
   expiry/CVV; test UPI `success@razorpay`). The widget then calls `/payments/verify`, which
   creates the confirmed order and runs fulfilment. No real money moves.

## 7. The important one: test the paid-but-no-order recovery

This is the path the new durable **cart snapshot** protects (a buyer pays, then closes the
tab before `/verify` runs; on a free host the process may even sleep in between). Simulate it
with no browser:

1. Do step 6.1–6.2 to get an `order_id`. A `payment_cart_snapshots` row is now written for it.
2. **Do NOT call `/verify`.** (This is the "tab closed" state — money captured at Razorpay,
   no DB order.)
3. **Fire the webhook** the way Razorpay would, signed with your local webhook secret:

   ```bash
   RAZORPAY_WEBHOOK_SECRET=local_webhook_secret \
     node scripts/local/sim-razorpay-webhook.mjs <order_id>
   ```

   Expect `200`. In the server logs you should see
   `Webhook: rebuilt paid order from cart snapshot`.
4. **Verify recovery:**
   - the buyer now has a confirmed order — `GET /api/v1/orders` with `TOKEN`, or the admin
     orders list;
   - the snapshot row is consumed:
     `SELECT status, consumed_at FROM payment_cart_snapshots WHERE razorpay_order_id='<order_id>';`
     → `consumed`.
5. **Idempotency check:** run the simulator again, or run it and *then* call `/verify` — you
   must still end up with exactly **one** order for that `order_id` (the unique index +
   `ErrDuplicateOrder` reuse). Confirm:
   `SELECT count(*) FROM orders WHERE razorpay_order_id='<order_id>';` → `1`.
6. **Manual-reconciliation case:** fire the simulator with an `order_id` that has no snapshot
   → the log reads `paid order has no matching DB order and no cart snapshot - needs manual
   reconciliation`, and no order is created. That is the only residual case the
   `PAYMENT_RECONCILIATION_RUNBOOK.md` now covers.

To test the real round trip instead of the simulator, run `ngrok http 8080`, register a
**Test-mode** webhook in Razorpay pointing at `https://<ngrok>/api/v1/webhooks/razorpay`
with secret `local_webhook_secret`, pay with a test card, and close the tab before verify.
(Test-mode webhooks are independent of your live webhooks — adding one changes nothing for
production.)

## 8. Magic Checkout (1CC) locally

Magic Checkout works the same way: `POST /api/v1/magic-checkout/create-order` with `TOKEN`
writes a snapshot (flow `"magic"`), and the webhook simulator rebuilds it identically. The
1CC callback signature stays **dormant** locally because `RAZORPAY_MAGIC_CHECKOUT_SECRET` is
unset, so the public callbacks respond without requiring a signature — no dashboard setup
needed to test the flow.

## 9. Teardown

```bash
docker-compose down          # keep volumes
docker-compose down -v       # also wipe local DB/Redis data
# stop the Firebase emulator and the backend with Ctrl-C
```

|------|-------|
| Backend | `http://localhost:8080` (Swagger `/docs`, health `/health`) |

**Nothing above changes any provider dashboard mode or sends any real OTP/payment.**
